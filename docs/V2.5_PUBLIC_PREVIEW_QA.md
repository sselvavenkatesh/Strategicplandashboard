## Loading-time analysis

Implemented in this preview:

1. The earlier frontend-to-API alias added an HTTP 307 redirect. The combined preview uses a single origin, eliminating that cross-host redirect/proxy path for reporting.
2. Summary previously awaited indicators before requesting initiatives for each goal. Both independent requests now run in parallel. Request count is unchanged, but one request stage is removed from each goal's critical path.
3. Goal detail code is loaded on demand. In the same local preview configuration, initial compressed JS decreased from 156.78 kB to 152.40 kB (about 2.8%); 5.5 kB compressed Goal detail code is deferred. This is a modest bundle improvement, not proof of a comparable page-load speedup.
4. API executes in Tokyo, near the database. The measured hosted API processing times above are approximately 29–59 ms. They exclude browser/network time, cold starts outside middleware and rendering.

Remaining performance opportunities, in priority order:

1. Measure real navigation/resource timings from browser DevTools under the same network/cache conditions. The cloud browser's restricted evaluation does not expose performance entries, and its locator timing cannot provide a reliable benchmark. Agent-side HTTP samples are proxy-affected and are not used to claim user-facing improvement.
2. If request latency dominates, add a public summary response combining all goal cards, avoiding eight per-goal indicator/initiative requests after bootstrap. Preserve existing calculations and role filtering.
3. Reuse already-loaded history/group data in Indicator popups and parallelize independent history/group requests. Currently some drill-down requests repeat previously fetched data.
4. Consider short-lived public reporting caches with explicit invalidation after future authorized edits. Do not cache authenticated data in a shared public cache.
5. Review per-repository database connections only if server timings identify them as material; current warm timings do not justify a broad database rewrite.

No verified end-to-end before/after speed percentage is claimed. Production comparison remains a controlled-browser measurement task.

### Indicator multi-year comparison

The indicator popup now offers Show All years. It displays up to the five latest available school years as narrow grouped bars per student group, with a consistent color per year and a year legend. The year selector is disabled while this mode is enabled and its previous selection is restored when disabled. Missing observations leave gaps; zero remains a valid value. Single-year mode retains its statewide average reference; multi-year mode omits that line to avoid mixing reference years. Indicator-card labels use stronger contrast and normal, heavier type. Both light and dark themes are covered by shared CSS.

No API or database changes. The component reuses the existing student-groups endpoint for each requested year, fetches years concurrently, and caches requests for the lifetime of the popup. Only the selected year is loaded until comparison is enabled. Requests from superseded selections cannot replace current results; errors offer retry. Four component/data tests cover year limits, missing values, selector behavior, legends, grouped colors and cache reuse. React build passes. Browser visual verification remains limited by Vercel protection.
