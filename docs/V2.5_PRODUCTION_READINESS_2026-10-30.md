3. Give the backend an explicit trusted canonical external origin and API prefix for the Netlify production deployment. Existing callback and origin validation use request.base_url/request.url.netloc. Preserve exact return-path checks, browser-bound OAuth state/PKCE, Secure HttpOnly cookies and same-origin mutation checks. Do not blindly trust client-supplied Forwarded/X-Forwarded-Host headers or weaken origin checks to make a proxy work. Verify cookie delivery on the actual branded hostname.
4. Netlify documents a 26-second external proxy timeout. Measure public AI and sign-in behavior through the final route; application-side 120-second timeouts do not increase the proxy limit. If responses exceed it, use a properly authenticated asynchronous job/polling contract or a verified supported streaming route before release. Do not switch to a cross-origin fetch without designing credential/cookie handling.
5. Run production-route checks for public/private visibility, assigned/unassigned Admin reads and writes, Super Admin configuration, logout/session revocation and Google sign-in. The owner completes Google consent interactively; do not claim provider acceptance from mocked tests.
6. Add shared deployment-wide login/AI abuse limits and verify browser security headers on actual responses. Local in-memory counters alone are not reliable across serverless instances. Close or explicitly accept the remaining medium findings in V2.5_SECURITY_ARCHITECTURE_REVIEW.md before calling the release security-cleared.
7. Publish via the existing Git production branches, verify Netlify's published commit and backend revision, then create an immutable V2.5 release/tag with release notes and tracked outstanding work. Preserve V2.4 source/deployment evidence for a fix-forward recovery. Do not mark a release frozen solely because a build passed.
