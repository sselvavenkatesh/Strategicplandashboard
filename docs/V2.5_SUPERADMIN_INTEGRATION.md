# V2.5 Super Admin integration — 29 October 2026

## Scope

Super Admin uses the existing district accounts and database. Saving changes affects the existing district data and therefore public dashboard values. Production frontend/API deployments remain unchanged. Stakeholder assignment controls future Admin data management, never public reporting visibility. Admin write authorization is a separate integration stage; this release implements Super Admin.

The preview banner, local-edit notices, example assignments, review-user selector and Super Admin/Admin switch are removed. The normal theme control remains. A real Super Admin sign-in is required before loading configuration or stakeholder accounts. Save/upload dialogs remain open on failure; success means a database transaction committed. Old session-storage drafts are never submitted to live saves.

## Reused implementation

- Existing validate_superadmin_login/session, eight-hour sessions and password hashes.
- Existing save_superadmin_configuration and update_superadmin_logo.
- Existing guarded delete_superadmin_goal.
- Existing validated bulk-upsert routines for new/imported reporting records.
- Existing public API calculations, role visibility and achievement contracts.

## Added API boundary

- POST /api/v1/superadmin/login: existing login with Secure, HttpOnly, SameSite=Strict session cookie. No password/session token is placed in browser storage.
- GET /api/v1/superadmin/session: current real account.
- GET /api/v1/superadmin/workspace: authenticated profile, masters, reporting data, active Admin names/IDs and assignments. No password hashes, OAuth secrets or other account fields.
- POST /api/v1/superadmin/workspace: one version-checked transaction for configuration, master edits/creation, assignments, reporting edits/imports or guarded deletion.
- POST /api/v1/superadmin/logout: revoke session and clear cookie.

## Database footprint

Three new RLS-enabled junction tables store multiselect owners; existing singular Stakeholder ID values are retained for compatibility. Three new session-validated functions provide read/save/logout. Anonymous/authenticated browser roles cannot execute these functions or access the junction tables. The existing reporting connection receives function execution only, without direct table UPDATE grants. No existing table was recreated, truncated or bulk migrated. The current database has one district; the new endpoint refuses ambiguous multi-district routing rather than guessing a tenant.

Only submitted changes are saved. Unchanged master definitions do not rewrite reporting rows. Names/goal links propagate to their reporting rows only when actually changed. Empty goal deletion still requires dependency checks and retains at least one goal. Revision checks reject stale saves with HTTP 409. All batch changes roll back on failure. Public selection remains Role=All and does not use assignment joins.

Displayed demonstration targets are preserved separately: an actual-only edit does not copy a demonstration target into the real district Target 1. An explicit canonical target edit updates that target and its existing public-demo overlay, keeping the public preview consistent.

## Follow-up: inheritance and compact tables

Goal owners now inherit per indicator/initiative by default. Empty resource selections mean Inherit from Goal; explicit nonempty subsets restrict only that resource. The selector lists only owners of the current Goal, and the SQL save function enforces the same rule. Goal owner changes/master moves remove obsolete explicit owners only for affected resources, without copying inherited assignments into child tables. Public visibility is unchanged.

Both master tables and Add dialogs expose the existing Indicator_short_name / Initiative_Short_name fields; saves preserve the stored value if an older caller omits the field. Initiative master edit controls align at the top of each row. Goal Name is the first reporting column, joined from the current master Goal. Reporting column headers sort ascending/descending (numeric actuals/targets, chronological dates, natural text, blanks last), before pagination. Sorting retains original row keys during edits. Fifteen reporting rows per page remain.

## Name-based uploads and uploaded public targets

Downloaded CSV templates now contain names and reporting fields only, removing Goal ID, Indicator/Initiative ID and Stakeholder ID. Import resolves the complete master name after Unicode normalization, case folding and whitespace collapsing, optionally scoped by Goal Name. Unknown names produce an actionable check-file error; ambiguous names require a Goal or distinct master names. Old templates remain readable, but supplied IDs never override the name match. Existing initiative row ownership is preserved on re-upload. Internal IDs remain the database keys and reporting updates retain original row keys.

Public target lookup and achievement now prefer the existing preview overlay when non-null and otherwise use the canonical uploaded Target 1 for the same school year. This fixes additional indicators absent from the seven-row demo overlay. No target data was copied or changed; only the summary function definition and API read query changed. Existing demo targets remain unchanged. The Supabase fallback client follows the same rule.
