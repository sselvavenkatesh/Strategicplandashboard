# User Management and SSO configuration

Super Admin has a User Management section for district Admin accounts. It supports adding users, editing name and login/provider emails, optional password creation/reset, disabling and re-enabling. Super Admin accounts are outside this Admin-account editor. Existing stakeholder assignments are retained when a user is disabled; existing Admin sessions are revoked on account edits. Inactive accounts cannot authenticate. User editing uses a server-checked revision and preserves the current primary keys. Two nullable columns were added to admin_users: Google Email and Microsoft Email. Existing accounts retain their values and provider mappings fall back to the primary Email when the provider-specific field is empty. Matching is provider-specific, case-insensitive and rejects ambiguous mappings. Only verified provider identities are passed to the mapping function; an email supplied by the browser is not authentication.

User management endpoints are GET/POST /api/v1/superadmin/users. They require the secure HttpOnly Super Admin cookie, check request origin on writes, validate the current database session, and never return passwords or password hashes. The save SQL runs with restricted EXECUTE grants and rejects non-Admin target records. New passwords are hashed using the existing bcrypt mechanism. Provider email collisions are checked under a table lock. Test accounts and session tokens used in SQL regression tests are rolled back.

The district configuration screen exposes Google Client ID, Google Auth ID, Microsoft Client ID, Microsoft Tenant ID and Microsoft Auth ID. SSO Credentials provides write-only password-masked client-secret fields, configured status and the exact callback URLs for the currently opened deployment. Save SSO Settings saves submitted secrets and the district configuration. Blank secret fields retain the existing value. Secret values are cleared from UI memory after a successful secret save and are not put in localStorage, URLs or frontend build variables. They are never returned by settings APIs. Client IDs are public OAuth identifiers and necessarily appear in authorization redirects; Auth ID is an optional legacy field and is not used by this server-side OAuth flow.

OAuth secrets are stored encrypted in Supabase Vault. District_Auth_Config stores only Vault UUID references; legacy plaintext columns are cleared during migration. Public, anon, authenticated and the API login role cannot directly select the configuration table. The server-only retrieval function can decrypt a secret for the OAuth token exchange. Public/browser roles cannot execute it. The authenticated Super Admin save function is the only UI write path. Settings responses use Cache-Control: no-store, and malformed-secret validation responses are redacted to avoid reflecting the submitted input. The public sign-in config endpoint returns the selected method and readiness flags only, without client IDs, Auth IDs, tenant IDs or secrets.

To enable Google SSO:
1. Register a Web application OAuth client and consent screen in Google Cloud; configure allowed/test users as appropriate.
2. Copy the Google Authorized Redirect URI shown in Super Admin into that OAuth client's authorized redirect URIs. It must match exactly. A preview at a different hostname requires its own registered callback; a stable preview/custom domain avoids repeated changes.
3. Enter the Google Client ID and Client Secret in Super Admin. Map each active Admin's Google Email in User Management.
4. Set Admin Signin Method to Google and save SSO settings. Test the real provider login before treating the rollout as complete. A configured status confirms local credentials exist, not that Google has accepted the redirect or consent setup.

Microsoft uses the corresponding redirect URI, Client ID, Tenant ID and client-secret value from Microsoft Entra, plus the Microsoft Email user mapping and the Microsoft sign-in method. Provider-side app registration, consent and secret rotation remain external steps.

At implementation time the district still uses Userbased sign-in; Google and Microsoft credentials are not configured. No real provider credentials were supplied, so live SSO sign-in was not claimed as tested or enabled. Mocked OAuth callback tests, 33 focused API tests, 36 Node regressions, user-management SQL rollback tests and Vault security rollback tests pass. Both React builds pass. The sign-in form now explicitly receives the dark theme class (previously only the session-check screen did); authenticated Admin workspaces keep their light-default independent theme preferences. Production frontend is not redeployed.
