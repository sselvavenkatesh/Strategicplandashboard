## Outsider threat model

Assume a visitor can read public source/JavaScript, discover the public Supabase URL/publishable key, call APIs outside the UI, vary IDs and forge payloads. A limited Admin may attempt unassigned writes or Super Admin functions. A compromised browser can attempt login swapping or token leakage. Public AI creates spend/concurrency risk. Future districts require separate authorization boundaries.

Trust boundaries: browser → Vercel protection → FastAPI → restricted database role → RLS/security-definer functions/Vault; separately browser → Supabase Data API/RPC; FastAPI → Ollama. Vercel preview protection does not protect the separate Supabase endpoint. UI filtering and CORS cannot replace database authorization. The shared database also serves V2.4, so policy changes need compatibility testing.

### SEC-01/02 — close every public data path

Public master policies check only their own Role; reporting policies omit parent/master checks. The normalized indicator view uses definer privileges and has no visibility predicate. History, student-group and latest-KPI SQL functions read that view without Role filtering. FastAPI wrappers check public master/Goal, but do not remove all private reporting rows or benchmarks returned by those functions. This additional API path is source-confirmed, not live-HTTP tested. Native AI uses separate, explicitly filtered queries.

Fix: enforce reporting row + master + Goal visibility consistently in base-table RLS, views, RPCs, benchmarks and aggregates. A security-invoker view helps only after underlying policies become correct. Revoke unused direct grants/functions after tracing V2.4 dependencies. The public Supabase key is intentionally public; hiding it is not a fix.

Acceptance: independently private Goal, master and reporting-row fixtures must reveal no records or derived values through anonymous tables/views/RPC/REST, FastAPI history/groups/targets/benchmarks/aggregates and public AI. Admin/Super Admin keep authorized visibility. Test against an isolated database before updating shared production policies; roll back fixtures.

### SEC-03/04 — consolidate authentication

Current workspace OAuth verifies provider identity and issues HttpOnly cookies, but compatibility branches remain part of the attack surface. One-use expiring state is insufficient against login CSRF without initiating-browser binding. Direct public SQL state creation bypasses HTTP start-handler return checks. Callback error redirects also trust stored destinations. Query-token redirects can leak through history/logs/downstream links. No authorization codes/session tokens were captured in this review.

Fix: backend-only state functions, short-lived browser-bound state plus PKCE, exact origin/path allowlist checks at start AND callback, no query-token redirects, and uniform active-account/role/revocation validation. Remove token APIs after compatibility review. Never use email-only identity as provider authentication.

Acceptance: callbacks without the initiating browser binding fail; replayed/expired/wrong-provider state fails; external destinations fail; disabled/revoked users fail on every route; redirects contain no tokens. Test Google and Microsoft separately against registered callbacks.

### SEC-05/06 — resource abuse and browser hardening

Add account/IP-aware login throttling, public AI quotas/concurrency/cost ceilings and telemetry limits. Enforce request sizes before parsing; current serialized-body checks occur afterward. Avoid blocking an entire school behind a shared NAT. Verify 429/Retry-After behavior with bounded staging tests, without expensive live load. Configure CSP/frame-ancestors/referrer/content-type protections and verify actual deployed responses while preserving required assets/OAuth. Define exact trusted origins and intentional missing-Origin behavior rather than treating the current guard as comprehensive CSRF protection.

### SEC-07–11 — governance and future isolation

Derive security-audit identities from validated sessions; label client telemetry untrusted. Define AI question/answer retention, deletion, backups, provider handling and incident response. Vault encryption protects storage but does not eliminate privileged backend/operator access. A key entered in Super Admin necessarily passes through that browser's form memory and TLS request; it must never be returned or persisted in browser storage afterward. Do not promise that it never touches the browser.

Before multi-district rollout, bind host and session to an allowlisted district/schema registry; isolate queries, caches, logs and secrets; safely qualify identifiers and test wrong-district tokens. A caller-supplied schema cannot grant access. Schema-per-district needs migration/backup discipline, not DB subfolders. Narrow account columns with a view/function or column privileges. Add typed API responses and automatic authorization coverage checks.

## Protections verified

- Modern sessions use separate Secure/HttpOnly/SameSite=Strict cookies; modern login JSON omits tokens. Workspace role/session/edit-assignment validation occurs server-side and in database functions.
- Admin reporting saves use stable row identities, transactional functions and optimistic revisions; unassigned writes are denied. Master/configuration/user changes require Super Admin.
- New AI/OAuth secret tables and credential functions are inaccessible to public/browser roles. Settings return status, not keys. Sensitive save validation is redacted. No real key was decrypted or copied for this review.
- Native public AI context filters row/master/Goal visibility; private context requires validated cookies. Body scope/district forgery is rejected. Account tables/keys are absent from model input; provider URL is fixed and no cross-user answer cache exists.
- Anonymous account/session/audit-log probes returned zero rows. RLS enabled without policies intentionally denies direct access to backend-only tables. Broad grants alone do not prove effective data access.
- Reviewed SQL calls bind values; reviewed React source revealed no intentional raw-HTML/eval path. This is targeted evidence, not proof against every injection issue.
- Vercel project deployment authentication is configured; it is separate from app permissions and direct Supabase access.
