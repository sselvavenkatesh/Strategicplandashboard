# V2.5 native AI and district credentials

The preview now contains a native FastAPI AI implementation using the same Ollama model default, exact system prompt, temperature 0.1, low thinking setting, plain-text cleanup and six district data sources as district-ai-preview. This reuses the existing model configuration; it does not retrain or replace the model. Responses can vary between calls, so identical wording is not guaranteed.

## Configuration

Open Super Admin at https://strategicplan-v25-preview-sselvavenkatesh.vercel.app/strategic-plan/demo/superadmin and select AI Configuration. Enter the district's existing Ollama API key and retain its existing model name (default gpt-oss:20b-cloud), then Save. A blank key retains the saved key. Keys are masked on entry, cleared from component state after saving, never returned by settings APIs, and never stored in browser storage or frontend build variables.

One shared District_AI_Config table contains one row per District ID: District ID, Ollama Secret ID, Ollama Model, Updated At. The actual key is encrypted in Supabase Vault. Only the restricted backend role can call the credential retrieval function. Super Admin configuration functions validate the existing active session. Public/browser roles cannot read the table, retrieve the key, save settings or read AI conversation logs. No district-specific Vercel environment variable is required.

The current app still has one district in the public schema. Backend lookup resolves that district from trusted database configuration and fails if routing is ambiguous. This is preparation for shared district configuration, not a completed schema-per-district migration. Future routing must bind the host and validated session to a district/schema through an allowlisted registry, and query the matching district data and credential row. A caller-supplied district ID or schema must never determine authorization.

## AI requests and visibility

GET /api/v1/ai/status returns only nativeReady. POST /api/v1/ai/ask accepts question and sessionId and returns the existing answer/sources/timings/modelMetrics contract. GET/POST /api/v1/superadmin/ai-settings read status or save write-only credentials.

Public requests receive Role=All goals, masters and reporting rows, including parent Goal checks. Counts are recomputed from visible masters. Authenticated Admin and Super Admin requests may use all district strategic records, regardless of edit assignments. Only validated HttpOnly server session cookies enable that scope; forged roles, district IDs or include_private body fields are rejected. Expired/invalid sessions cannot receive private context. Data is read as a consistent database snapshot and has no shared response cache or cross-user conversation history. No account records, hashes, OAuth settings or API keys are supplied to the model.

The existing prompt, in-scope checks, model options and response cleanup are preserved. Indicator IDs are replaced with readable names on the backend using the same visibility-scoped context, including private indicators for authorized users. Provider failures produce a generic response and do not echo credentials or context. AI audit records use the existing protected AI_Conversation_Log table through a narrow server-only function; audit failures do not discard an otherwise valid answer.

## Activation and verification

Until a district key is saved, nativeReady is false and the frontend retains the current working district-ai-preview flow. After the key is saved, subsequent questions automatically use native FastAPI; no redeployment is needed. A saved-key flag confirms storage, not provider acceptance. Real Ollama response comparison must be completed after the owner enters the actual key. No provider secret was copied out of the existing Edge Function environment.

Validation: 59 focused API tests passed, including original-prompt parity, provider payload/settings, public/Admin/Super Admin scopes, invalid sessions, forged scope rejection, cross-origin checks, confidential validation errors and plain-text formatting. Real database rollback tests verified Vault save/retain behavior, restricted grants, masked settings, protected logs, private parent Goals, private masters and private reporting data. All test data and temporary session changes were rolled back. React build passed. Business record counts remain 4 Goals, 7 Indicators, 11 Initiatives, 193 indicator rows and 132 initiative rows. The migration adds only a settings table and server functions; it does not rewrite business records. Production frontend and Edge Functions remain unchanged.

Security advisor notes for the new settings table and existing audit table report RLS with no policies; this is intentional default-deny access through restricted server functions. Existing legacy view/RPC advisor findings were not changed as part of this migration.
