# V2.5 Admin integration — 29 October 2026

Admin uses existing active district Admin accounts, password verification and session storage tables. No existing account credentials were retrieved, reset or replaced. The legacy validator looked up User ID although the existing login creates sessions with numeric account ID; the new preview identity function safely supports numeric IDs and legacy nonnumeric User IDs, checks account activity/role and expiration on every request. Existing legacy functions remain unchanged.

## Functional behavior

- `/admin` requires real sign-in and loads only assigned reporting data. It never submits session-storage prototype drafts.
- Goal ownership grants indicator/initiative access by default. A nonempty resource stakeholder subset restricts only that resource. Both parent Goal membership and applicable resource membership are checked in SQL for every read/write.
- District/plan and assigned Goal/master definitions are read only. Names, short names, Goal links, logo, configuration and assignments remain Super Admin-only.
- Admin can change actuals, targets, initiative dates/status/action items and upload new reporting rows for assigned masters. CSV name matching and ID-free templates are reused. Existing reporting keys, Role, school and ownership cannot be changed through an Admin edit. New rows use the master's Role.
- Original row keys support action-item rename without duplication. Batch failures roll back entirely. Revisions reject concurrent changes, including assignment removal.
- Actual-only edits preserve raw real targets beneath demo overlays. Explicit canonical target changes synchronize an existing overlay. Public visibility continues to use Role=All, independent of stakeholder assignments.
- The public sign-in and header use the same FastAPI session in V2.5. The Admin workspace can return to the full public dashboard. Admin and Super Admin cookies are separate, Secure/HttpOnly/SameSite=Strict, eight-hour cookies, with server-side logout.

## API

| Endpoint | Function |
|---|---|
| POST `/api/v1/admin/login` | Existing Admin account/password verification; cookie session |
| GET `/api/v1/admin/session` | Current active account |
| GET `/api/v1/admin/workspace` | Read-only configuration, scoped masters/reporting data |
| POST `/api/v1/admin/workspace` | Revision-checked assigned reporting edits/uploads only |
| POST `/api/v1/admin/logout` | Revoke session and clear cookie |

Google/Microsoft use the existing verified FastAPI OAuth flow. Workspace callbacks issue the same HttpOnly cookie and do not place session tokens in URLs. The provider must have the callback URL configured for the deployment. Current district sign-in method is Userbased; provider exchanges are covered by mocked contract checks, not a live provider login.

## Database footprint

Four new private execution-only functions: identity, resource authorization, scoped snapshot and transactional reporting save. No new tables, public/browser grants or direct table write privileges. Snapshot excludes other account/stakeholder details and OAuth configuration. Helpers have PUBLIC/anon/authenticated execution revoked; only the server reporting role can invoke authenticated boundaries. Advisors found no new Admin-function warnings.
