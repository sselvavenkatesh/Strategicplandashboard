# V2.5 — Admin and Super Admin UI review

Status: UI prototype, pending product-owner review. Current production remains at commit `2a530072fa723942570e414adad4dcd7a502653e` on `react-dashboard`.

## Review routes

- `/superadmin`: district overview, Strategic Plan Configuration, Goal Master, Indicator Master, Initiative Master, stakeholder multiselects, reporting-data editors.
- `/admin`: the same workspace structure with read-only district configuration, Assigned Goals, Assigned Indicators and Assigned Initiatives. Use “Review as” to select one of the five existing active Admins.
- Both routes also work below `/strategic-plan/demo`.

`VITE_V25_UI_PREVIEW=true` enables these UI review routes. The flag is scoped to the `v2.5-ui` Netlify branch context. Without the flag, the original Admin and Super Admin routes remain in use. This flag must not be enabled for a production release until authenticated FastAPI integration is complete.

## Data and saving

The prototype reads the existing public district profile, canonical `Role=All` master records, indicator reporting records, initiative reporting records, and approved demo targets. Only safe display fields are requested. Existing active Admin names and IDs are a display-only snapshot obtained on 28 October 2026; emails, credentials and sessions are not included.

Every stakeholder dropdown starts at **None**. All assignments, profile drafts and reporting edits are stored in this browser tab's versioned session storage. “Save preview changes” confirms a local save; no production write endpoint is called. “Reset preview” clears those drafts. A new tab starts without assignments. No login impersonation or real authenticated authorization is implemented by the review-user selector.

For a quick comparison, select **Load example assignments** in the Super Admin overview. John and Sarah receive Goal 1; John gets explicit Indicator ID1 and Initiative IN1 access. Sarah inherits all Goal 1 indicators and initiatives. The other three Admins each receive another goal. These examples are never written to the database.

## Agreed access behaviour

- Goals may have multiple stakeholders, using existing Admin accounts.
- Indicator and initiative assignments are independent.
- For a given Admin and resource type, no explicit selections means access is inherited from their assigned goals.
- If that Admin has explicit selections for that type, only those selected resources are visible/editable, across all goals. Clearing their final explicit selection restores goal inheritance.
- A direct assignment can grant an individual item without assigning its whole goal.
- Admins can edit actuals, targets, dates, statuses and action items only within their displayed scope. Master definitions and assignments remain Super Admin-only.
- Each district will have its own Super Admin after backend integration. The frontend access model is a UI demonstration, not a substitute for server authorization.

## Compact layout refinement

District configuration and Goal Master use separate tabs. Indicator/Initiative Master and reporting data also use separate tabs. Master lists show five items per page; reporting data shows eight. All items remain available through pagination and filters. Stakeholder menus float outside the table scroll container so compact tables do not need blank space below them. Save controls use a short “Save” label and intrinsic width. Explanatory placeholder prose is removed; actual district/goal content, field labels, status badges and a brief “Local edits only” preview label remain.

## Master creation, renaming and bulk data UI

Super Admin can add indicators and initiatives through compact dialogs, with generated local IDs and a required goal. Existing master names can be edited; names are resolved from masters in both Admin and Super Admin data views, so a rename does not create duplicate data. Goal reassignment of an existing item is intentionally excluded from this name-editing change. New items start with no explicit stakeholder selection and therefore follow the established goal inheritance rules.

Both reporting data tabs provide Download Template and Upload Data. The downloaded CSV column names and order match the existing Super Admin templates. Uploads validate headers, required fields, allowed master IDs, goal membership, duplicate keys and a 2 MB/5,000-row limit. A compact review dialog shows new/update counts before applying changes to local preview state. Existing keys update reporting rows; unmatched keys add reporting rows. Admin uploads accept only resources already in their scope. This UI prototype handles canonical Role All reporting records; other roles produce an explicit validation error. Authenticated bulk writes and any expanded legacy role handling remain part of FastAPI implementation after review.

Validation now includes eight CSV parsing, scope, matching and preservation tests in addition to the seven access-rule tests. No live database writes are performed.
