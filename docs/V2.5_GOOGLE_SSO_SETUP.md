1. Open Google Cloud Console and select or create the project for Strategic Plan Dashboard.
2. In Google Auth Platform, configure Branding: app name Strategic Plan Dashboard, support email and developer contact email. In Audience, choose External for the personal Gmail account. Keep Testing for the initial check and add s.selvavenkatesh@gmail.com as a test user.
3. In Data Access, request only the identity scopes openid, email and profile. No Gmail, Drive or other data-access scope is needed.
4. In Clients, create an OAuth client of type Web application. Add the exact Google Authorized Redirect URI shown in Super Admin. For the stable V2.5 preview the callback is:

   https://strategicplan-v25-preview-sselvavenkatesh.vercel.app/api/v1/auth/admin/oauth/google/callback

5. Copy the Client ID and Client Secret directly into Super Admin, Strategic Plan Configuration, District & Strategic Plan. Select Google as Admin Signin Method and click Save. This single action securely saves the secret first, then validates and saves the district configuration. Auth ID is an optional legacy field and is not required by the current server-side Google flow. Do not put the secret in a URL, frontend file, email or chat.
6. Open the Admin sign-in page on the same stable preview hostname and select Google SSO using s.selvavenkatesh@gmail.com. A successful sign-in maps to admin1's existing permissions. The authorized redirect URI must exactly match, including scheme, hostname and path.

Google configuration reference: https://developers.google.com/workspace/guides/configure-oauth-consent and https://developers.google.com/identity/protocols/oauth2/web-server

## Application behavior

Userbased remains the default configuration value. Selecting Google requires a Client ID and saved Client Secret. Selecting Microsoft requires Client ID, Tenant ID and saved Client Secret. Validation runs on the server for every configuration save as well as in the SSO settings UI. Admins can always sign in with their existing email and password, alongside any configured Google or Microsoft provider. Provider availability depends on complete credentials rather than the single legacy method selection. The compact login widget labels these options Sign in with Google and Sign in with Microsoft, with provider logos and an or divider. Super Admin sign-in remains password-based. Accounts created without a password must use their configured provider until a Super Admin sets a password.

The minimum-length and character-composition rules were removed from Admin password management. New password hashes use bcrypt over a SHA-256 prehash with a version prefix, supporting long strings without bcrypt truncation. Existing hashes and passwords are preserved and still authenticate through the legacy verification path. Client secrets remain in Vault and are never returned in settings responses. The authenticated SSO status response contains only boolean saved-secret indicators, not secret values.

Validation: 33 focused API tests; database rollback coverage for short and long mixed-character passwords, non-truncation, required provider configuration and completed Google/Microsoft setup. All test credentials and method changes were rolled back. Real Google sign-in awaits the user's provider registration and actual credentials.
